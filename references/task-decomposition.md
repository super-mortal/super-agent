# 任务划分

## 粒度

| 维度 | 太粗 | 恰好 | 太细 |
|---|---|---|---|
| 任务范围 | 一整套功能 | 单个功能模块 | 某个函数 / 某一行 |
| dev 一次会话 | 超出会话上下文 | 一次会话内能完成（含自测） | 太小、切换成本高 |
| 可验证性 | 难以测试 | 可独立验证 | 缺乏独立验证点 |

**必须满足**：

- 每个任务是单个功能模块
- dev 一次会话内能完成（含自测）
- 可独立运行 + 独立验证

## 顺序

```
P0: 框架搭建                    → 固定编号 task0（planner 完成，不测试、不提交）
  → 项目初始化、公共组件、主题、路由
  → 不计入开发任务序列

P1~PN: 逐功能开发               → 从 task1 起，全局连续编号
  → 每个 P 阶段一个功能
  → 每子任务走完整 dev → test → 修正循环

最后一个 P 阶段: 整体集成测试
  → 跨功能衔接与全局一致性
```

## 编号规则

| 编号 | 归谁 | 进 dev / test 循环 | 提交 |
|---|---|---|---|
| `task0` | planner（P0 前置工作） | 否，状态直接 `✅` | 否 |
| `task1`…`taskN` | developer + tester | 是 | 是 |

- **`task0` 不占开发任务序号**：一个有 12 个开发任务的计划，编号是 `task1`…`task12`，不是 `task2`…`task13`。
- **task0 不承载业务代码**：P0 若产出需要版本化的代码（骨架、依赖清单、公共组件），必须拆成 `task1` 交给 developer，否则会留下游离未提交改动。
- **编号即提交序号**：`task1` 对应 git log 第一条提交，`taskN` 对应第 N 条，看提交历史就能读出进度。
- **编号生成后不改**：任务拆分时新增编号、不回填空号；已完成的编号不重排。
- **旧计划不重编号**：已经生成的 dev-plan（P0 占用 `task1` 的那种）保持原样，避免打乱测试报告文件名与提交历史；本规则只对新建计划生效。

## 依赖

- 依赖关系用于确定任务顺序并向 tester 传递风险，但不能中断整个批次。
- 上游任务为 `✅` 时，下游任务按正常路径执行。
- 上游任务为 `⚠️` 或 `❌` 时，下游任务仍然继续，但主智能体必须在 prompt 中明确提示依赖风险。
- 下游 tester 必须额外验证相关集成假设，不能只验证当前模块的局部行为。
- 公共组件（主题、工具函数、错误码常量）放 P0
- 发现新依赖时更新 `dev-plan.md` 的依赖字段并调整执行顺序，不停止整个批次
- 为跑完整个项目，允许在上游未完全通过时继续下游任务，但必须在日志和最终报告中保留风险记录

## dev-plan.md 字段

| 字段 | 必填 | 含义 |
|---|---|---|
| 任务 | 是 | `task0` 固定为 planner 前置工作；开发任务 `task1` / `task2` / `task3` 全局连续编号，不使用 `#` 列 |
| 阶段 | 是 | P0 / P1 / P2 / PN |
| 任务内容 | 是 | 一句话功能描述（"可独立验证的功能模块"） |
| 状态 | 是 | ⏳ 待办 / 🔄 进行中 / ✅ 完成 / ⚠️ 未通过（已放行） / ❌ 阻塞 |
| 涉及需求文档章节 | 是 | §X.Y（主智能体据此告诉子智能体读哪节） |
| 依赖 | 是 | 上游任务编号（无则填 —） |

## 计划审查基线（plan-reviewer 用）

planner 写完计划后，由 `agents/plan-reviewer.md` 按本节核对。顺序问题不是"看起来顺不顺"，而是"这个任务开工时，它需要的东西是否已经存在"。

### 典型安全顺序

```
配置 / 环境 / 依赖清单
   → 数据层（schema、migration、model）
      → 服务层与内部逻辑
         → 接口层（路由、参数校验、错误码）
            → 前端 / UI / 交互
               → 集成测试（跨功能衔接、全局一致性）
```

跨越这条链时，"后面的任务依赖前面的产物"，依赖列必须写实。可并行的横向模块（如两个互不引用的功能页）允许并列，但一旦共享同一份表结构或公共组件，就存在隐藏依赖，必须显式写出或把公共件提到 P0/task1。

### 高频倒置（出现即判阻塞）

| 症状 | 为什么必须改 |
|---|---|
| 先做"查询接口"，后建表/迁移 | 接口无数据可查，dev 只能造假数据，tester 也测不出真问题 |
| 先做页面，后做接口 | 前端联调阶段整块重做 |
| 鉴权改造排在业务功能之后 | 业务代码要写两遍（先无鉴权版，再改一遍） |
| 公共组件 / 主题 / 工具函数散落在各功能任务里各写一遍 | 重复实现 + 后期统一改造成本翻倍 |
| 依赖列填 `—`，但任务内容明确要调用另一个任务的接口 | 顺序失去约束，执行全凭运气 |
| 数据迁移与功能开发混在同一任务 | 失败时无法判断回滚点，风险不可控 |
| 计划里按"猜测的第三方字段"直接开工，无核验任务 | 协议一变，整条链路返工 |

### 不算阻塞的情况（避免过度审查）

- 粒度略大但一次会话仍能完成 → 建议拆分，不阻塞
- 任务标题措辞不统一、备注不完整 → 建议，不阻塞
- 顺序可优化 1~2 位但两种顺序都能跑通 → 建议，不阻塞
- greenfield 项目里"代码尚不存在" → 正常现象，不作为阻塞项
