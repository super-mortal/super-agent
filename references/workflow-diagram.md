## 5. 简明对照

| 场景 | 启动方式 |
|---|---|
| 第一次开发 | 新 Agent |
| 修 bug | resume 同开发 Agent |
| 第一次测试 | 新 Agent |
| 重测 | resume 同测试 Agent |
| 新任务开发 | 新 Agent（**不复用旧任务**） |
| 新任务测试 | 新 Agent（**不复用旧任务**） |
| 计划里的 `task0` | planner 的前置工作，状态恒为 ✅：取任务时直接跳过，不启动 dev/tester、不提交、不产生测试报告 |
| 任务判定完成（✅ / ⚠️ / ❌） | 主智能体执行 `commit_task.py` 提交，三态都提交；⚠️ 语义是「未通过（已放行）」，不是「通过但有隐患」 |
| 计划完成、循环开始前 | 询问推送策略，写入 `run.json.push_policy`；用户不选默认 `batch-end` |
| 项目不是 git 仓库 / 没有远端 | `push_policy = none`，不提交也不推送，流程照常推进 |
| 批次全部完成（batch-end） | 写 final-report → 列待推清单 → 用户确认后才 `push_task.py --confirm` |
| 批次全部完成（per-task） | 提交时已逐条推完，只汇报最终状态 |

## 6. 提交与推送

先定策略，再进循环。提交发生在每个任务的判定之后；推送时机由阶段 B2 选定的 `push_policy` 决定。

```
[计划完成] ─► 探活（是否仓库 / 是否有远端）
   │
   ├─ 不是 git 仓库 ──► push_policy = none ─► 跳过全部 git 动作（不提交不推送）
   ├─ 无远端        ──► push_policy = none ─► 同上：没有出口的存档没有意义
   └─ 正常          ──► 询问用户
                          ├─ A) 逐任务推送 ──► push_policy = per-task
                          └─ B) 批次末推送 ──► push_policy = batch-end（默认）

[任务判定完成]
   │
   │  （push_policy = none 时整段跳过：不提交、不推送，直接取下一个任务）
   │
   ├─ ✅ PASS       ─┐
   ├─ ⚠️ 用尽 5 轮   ─┼─► commit_task.py ─► OK: {hash} ─► 写 main-log
   └─ ❌ 未能判定    ─┘                                   │
                                                          ├─ per-task  ─► push_task.py --confirm
                                                          │                 ├─ OK      ─► 取下一个任务
                                                          │                 └─ BLOCKED ─► 停手报告，剩余改为 batch-end
                                                          └─ batch-end ─► 取下一个任务

[全部任务完成] ─► final-report.md
                     │
                     ├─ batch-end ─► push_task.py（预览）─► 列待推清单询问用户
                     │                                       ├─ 确认   ─► --confirm ─► OK / BLOCKED / ERROR
                     │                                       └─ 不确认 ─► 提交保留在本地
                     └─ per-task  ─► 汇报已推条数 + 剩余待推（通常为 0）
```

推送命令固定为 `git push -u origin {branch}`，由 `push_task.py` 内部执行。前置判定与探活：

| 情形 | 脚本怎么判断 | 结果 |
|---|---|---|
| 不是 git 仓库 | `rev-parse --git-dir` 失败 | `SKIP`，整套 git 跳过 |
| 没有配置远端 | `git remote` 为空 | `SKIP`，不提交也不推送 |
| 远端还没有该分支 | `git ls-remote --heads origin {branch}` 为空 | 正常首推，`-u` 绑定 upstream |
| 有分支但本地没绑 upstream | `@{u}` 解析失败 | 同样用 `-u` 推 |
| 远端领先本地 | `git merge-base --is-ancestor origin/{branch} HEAD` 为假 / `rev-list HEAD..origin` > 0 | `BLOCKED`，不推、不 force |
| 没有待推提交 | `rev-list origin/{branch}..HEAD` 为 0 | `SKIP` |
| 认证 / 网络失败 | git 退出码非 0（已禁交互输入） | `ERROR`，原样上报 |

提交消息：

| 判定 | 提交消息 |
|---|---|
| ✅ PASS | `task7: 历史记录封面持久化` |
| ⚠️ 用尽 5 轮 | `task7 [未通过]: 历史记录封面持久化` |
| ❌ 未能判定 | `task7 [未能判定]: 历史记录封面持久化` |

消息只有标题一行，不带 `test-rounds` / `test-report` / `run` 正文。

提交范围只用 developer 返回的修改文件路径，`.super-agent/` 过程产物不入库。

## 7. 提交身份确认

部分 IDE 会在**进程级**注入身份环境变量，让 commit 署名成工具名而不是用户本人
（Trae 已知注入 `GIT_COMMITTER_NAME=trae-solo-agent`；Cursor / Copilot 一类还会追加
`Co-authored-by`）。这类注入不改 `.gitconfig`，所以光看配置排查不出来。

检测方式很简单——比两个值：

```
配置身份  git config user.name / user.email
实际身份  git var GIT_COMMITTER_IDENT     ← 受环境变量影响
两者不同  说明有东西在覆盖 → 需要问用户
```

### 时机：加载阶段（阶段 A），早于任何提交

```
[技能加载]
   │
   ▼
git_identity.py --repo {project_root}
   │
   ├─ OK: 无需询问      ─► 一致，或已有记录 ─► 继续
   ├─ SKIP: 不是仓库    ─► 记"未启用 git" ─► 继续
   └─ ASK: 存在冲突     ─► 问用户三选一
                             │
                             ├─ A) 用 IDE 默认，本项目不再提示 ─► --set ide  （项目级）
                             ├─ B) 本轮用我自己的              ─► run.json    （仅本批）
                             └─ C) 本项目以后都用我的          ─► --set user （项目级）
                                     │
                                     ▼
                              记一行 main-log，继续初始化
```

### 记录与跳过

| 选择 | 存放位置 | 下次加载 |
|---|---|---|
| A `ide` | `{project_root}/.super-agent/preferences.json` | 本项目读到即 `OK`，**不再问**，署名 IDE |
| B `user`（本轮） | 本批次 `run.json.identity_policy`；本批提交统一带 `--identity user` | 新批次没有记录 → 若仍有冲突会再问 |
| C `user`（本项目以后） | `{project_root}/.super-agent/preferences.json` | 本项目读到即 `OK`，**不再问**，署名用户 |

### 提交时的行为

`commit_task.py` 按记录执行（`--identity auto` 读偏好，缺省 `user`）：

| 策略 | 行为 | 输出 |
|---|---|---|
| `user` | 剔除 `GIT_AUTHOR_*` / `GIT_COMMITTER_*`，用 git config 身份 + `-c` / `--author` 强制写入 | `OK: {hash}`，回读不符则 `WARN` |
| `ide` | 保留注入，让 IDE 署名 | `OK: {hash}` + `NOTE: 本次使用 IDE / 环境身份 …` |

诊断命令：

```bash
python {skill_root}/scripts/git_identity.py --repo {project_root}
# OK: 无需询问（配置身份与实际提交身份一致）
#   配置身份：super-mortal <2169702639@qq.com>
#   实际提交：super-mortal <2169702639@qq.com>

python {skill_root}/scripts/git_identity.py --clear   # 忘掉记录，下次重新问
```
